# SayHelp 第 6 章：正式分流器与退款售后子流程设计

日期：2026-10-10（Asia/Shanghai）。状态：设计草案，等待用户书面审阅；不是实施计划或完成报告。

## 1. 目标与已确认边界

把第 5 章占位分流器升级为可验证、可恢复的正式节点。用户从物流切换到退款，再回到物流，每轮使用当前问题重新判断意图；历史只帮助解释指代，不能把上一轮意图强加给本轮。

用户明确要求：

- 复用聊天上游完成指代消解和保守改写；已完整、明确的问题原样透传。
- 仅 Jev System One 的 choice 接口进行八类单标签意图识别；不使用通用 LLM 分类、few-shot 分类或另一个分类模型兜底。
- Jev state 仅为处理后的完整 Query；业务输出只含 intent、confidence。分类失败及低置信由集中代码策略处理。
- 退款退货与售后先拿订单，再在检索侧扩写并强制查政策，最后交主力 Agent 判断。知识入库不为扩写复制多份。
- 缺客户ID由主力 Agent 询问。订单号可询问或由聊天卡片点选回填；缺失时不猜。退款原因只在提交表单时从固定类目选择。
- 订单卡片使用 LangGraph interrupt，选择后恢复；前端直接按效果迭代，不套 brainstorm/TDD/code review。
- 后端走 Superpowers；纯 Prompt、criteria、数据部分用标注评估替代 TDD。无跨会话记忆、微调、额外本地分类模型。

用户提供的数据源位于 knowledge_db；本章不增加登录体系。客户ID是用户声明的查询范围，不等同于经过认证的身份。

## 2. 实现基线与方案取舍

实现基线为 codex/ch05-workflow 的 fe16a9c，而非目前只有第 5 章设计/计划的 main。沿用单 worker、MySQL 业务存储、官方 SQLite checkpointer、现有 Agent 子图与检索组件。实现阶段创建隔离分支，带入用户当前提供的文档快照，不覆盖 main 的其他未提交修改。

考虑的接法：

1. **采用：外层图增加明确节点。** 查询理解、Jev、置信策略、选单、查订单、政策检索各有独立边界；容易验证执行顺序和恢复语义。
2. 把所有逻辑塞进 classifier：改动较少，但分类会混入追问、检索和业务副作用，不满足独立分类节点要求。
3. 新建第二套聊天 Workflow：隔离较强，但重复历史、SSE、持久化与预算处理，不采用。

不更换用户指定技术。查证具体 API 与基线版本不兼容时先说明矛盾并询问，不自行升级或换框架。

订单、物流和原因枚举不进入向量库。模型不得从检索近似匹配推断订单身份。解析器校验表头、字段数、ID唯一性、同单客户一致性、金额和数量范围、时间格式及物流关联；错误提供文件和行号，不悄悄跳过记录。时间为带 Asia/Shanghai 语义的值，金额使用十进制金额表示。

同一订单多商品项时，选择身份为 customer_id + order_id + item_id。金额字段按商品项实付总额解释，不再乘数量；退款上限取该字段。缺少拆封情况、质量检测、购买页特别约定等事实时标为未知，由 Agent 给条件判断或澄清，不按商品名称补造事实。

资料目录已删除 product-faq.md、product-specs.md 并新增 product-specifications.md。需更新入库白名单、来源分类、manifest 与引用读取白名单，仍只允许明确列出的知识文件。政策与商品重新建索引后才能使用，不修改或覆写原 ch04 校准结果。

政策生效日期与订单购买时间均保留。当前政策不能无证据地被称为购买当时的约定；版本适用不明时明确限制结论。数据间时间或状态冲突不得通过静默修改源文件修复。

## 4. 查询理解

新增独立 QueryResolver，输入当前原话、同一会话内有界历史、已确认的客户/订单商品上下文。复用当前聊天模型，一次处理指代消解和口语归一化。

内部结构为 query、changed、unresolved_references；changed=false 时代码返回输入原文，保留字符与标点。仅允许补全历史有唯一依据的对象，或纠正影响检索的模糊口语。不追求风格润色，不改变否定、数量、型号、时间、问题目标；ID只能来自用户已提供的信息或已校验的点选结果。

历史包含多个可能对象时，不猜其中一件；保留未解指代标记。动作明确的“这个能退吗”仍可交给 Jev 判断退款意图，执行阶段再选商品；问题不可能在缺失事实时伪装成已完整消解。需求澄清由主力 Agent 完成。查询理解异常进入显式兜底，不把失败改写当作成功消解。

用户新一轮“先不退了，查下物流”必须保留否定与新目标。确认的订单可在同一会话明确相关时复用，但不能仅因为上一轮选过商品，就把之后所有“这个”绑定到它。

## 5. Jev 独立意图节点

官方 HTTP 接口为 POST https://api.typesafe.ai/v1/systemone，Bearer 鉴权。复用已有 HTTP 客户端依赖封装独立 JevIntentClassifier，不将 Jev 实现散入图节点或 ModelService 的普通聊天分类方法。

请求只有集中配置读取的 model、纯 Query 字符串 state，以及一个名为 intent 的 questions 条目。该问题 type=choice，instructions 仅说明判断当前主要诉求，criteria 包含且只包含以下八个中文键，无 few-shot：

| 类别 | 判断边界 |
|---|---|
| 物流 | 发货、配送、到货、运输轨迹、签收与物流异常查询；明确以退款为当前目标时归退款退货 |
| 订单 | 交易信息、支付、发票、地址修改、订单取消等订单操作；退款金额、退款进度、退货退款归退款退货 |
| 商品咨询 | 购买前后普通规格、功能、兼容性、使用方法；已发生的故障、维修、保修申请归售后 |
| 退款退货 | 退款/退货资格、条件、申请、金额、到账及进度；损坏但明确要求退款仍归此类 |
| 售后 | 故障处理、维修、保修、换货、补发、售后服务；明确要求退款/退货归退款退货 |
| 投诉 | 当前主要请求为投诉、追责、服务争议升级；仅有情绪或抱怨不覆盖明确物流/退款诉求 |
| 闲聊 | 问候、感谢、普通社交；业务外专业问题或不明文本不强行视为闲聊 |
| 其他 | 范围外、乱码、不足以确定目标，或相互独立多诉求且无明确主次；允许真实弃权 |

意图针对当前诉求，最后的明确纠正覆盖已否定的诉求；无需为槽位未齐改变意图。上述边界是初始 criteria，必须通过中文标注评估验证。

适配器验证 answers.intent.type、八类枚举、完整概率键集合、概率/置信度有限且在范围内、概率和及 choice 一致性。异常结构拒绝使用。保留原始概率与模型版本供服务端评估，不向下游暴露原结构。

成功分类的公开契约严格为：

```json
{"intent":"退款退货","confidence":0.0}
```

上面 0.0 仅展示字段类型，不是阈值或真实结果。Jev 的 confidence 为分布统计量，不等于正确率，也不使用最大 probability 替代。

### 配置、模型确认与失败语义

- 密钥：TYPESAFE_API_KEY，仅服务端环境或被忽略的 .env。
- 集中配置：JEV_MODEL、API基础地址、超时、有限重试、意图校准文件路径与兜底策略；不在业务逻辑散落模型名。
- 实现 Jev 前先用凭据实际 GET /v1/models，记录非敏感返回；模型列表项为 name，不套用其他供应商 data[].id 格式。依据实际返回和官方版本映射确定配置版本，评估后固定版本；别名漂移须使校准失效。
- 独立 IntentPolicy 统一处理 unknown、low_confidence、timeout、provider_error、invalid_response、calibration_missing、calibration_mismatch。禁止回调普通 LLM 再分类。
- 有有效 Jev 结果但低于阈值时，公开 intent 变为“其他”，confidence 保留实际返回值。API失败时为“其他”及 0.0；服务端另存明确 failure reason，UI显示暂时无法判断，不能呈现成普通高置信分类。
- 路由只消费公开 decision 与内部策略状态，不消费 Jev answers/probabilities。状态是 Workflow 控制字段，不添加到上述双字段 JSON。
- 配置缺失/版本与校准不符时关闭自动业务路由并明确报告，不能默认为通过。验收命令发现缺失即失败，不能借固定回复宣称上线可用。

## 6. 图的执行顺序

```text
当前消息 → 查询理解 → Jev分类 → IntentPolicy → 固定路由
  物流/订单 → 主力Agent（缺客户ID/订单号时询问，工具按匹配关系读取）
  商品咨询 → 单Query检索及证据闸 → 主力Agent
  退款退货/售后 → 确定性子流程：
    补客户ID → 确定订单商品项（缺失则interrupt选卡）
    → 读取并校验订单 → Query扩写 → 强制政策检索/去重/重排
    → 证据闸 → 主力Agent判断或澄清 → 答复/退款表单建议
  投诉 → 既有投诉响应与动作建议
  闲聊 → 既有固定问候
  其他/失败/低置信 → 集中兜底，不进入退款业务路径
```

缺客户ID时，主力 Agent 的受限澄清步骤询问缺失标识，代码明确禁止查订单、扩写、检索与退款动作。该步骤只是收集槽位，不提前进行退款判断。提供完整标识的请求直接跳过澄清。

执行阶段客户ID/订单号回复属于待处理请求的槽位补充，不送入 Jev 作为新业务问题重新分类。点选卡片通过专门恢复接口处理。普通聊天文本由上下文理解区分 slot_reply 与 new_request，不能将任何回复都当作客户ID；它不返回八类意图。若是新诉求，结束旧等待再走正常 Jev 分类。难以确定时保留等待并由主力 Agent 澄清。

## 7. 多查询政策检索

仅 intent 为退款退货或售后时扩写；简单 FAQ 不扩。必须在真实订单读取成功后执行。扩写输入含完整问题及必要商品属性，不加入未经证实的质量问题、签收时间或客户意愿。

LLM 输出强制 JSON，唯一字段 queries，为 3 条非空字符串数组，分别覆盖资格/期限、限制/例外、办理/费用；语义不适用的侧重点改为该问题相关的不同政策角度，不捏造前提。校验额外字段、长度、空值、重复、ID/数量/否定约束。上游支持结构化输出时使用其已查证接口，同时保留服务端严格校验；不支持时须先报告接口限制，不擅自换模型。

检索使用原完整 Query 加 3 条扩写，文本去重后最多 4 条，调用次数与并发有上限。扩写失败进入明确兜底，本章不静默当作正常多查询检索。

每条调用现有 hybrid 召回，收集 candidates（不是只用每条最终前10），限定退款与售后政策来源；合并时按稳定 chunk_id 去重。保留各查询命中位置，用倒数排名融合排序截取有界候选，再以原完整 Query 进行一次统一 rerank，避免比较不同 query 的重排分数。完整条款与引用按现有证据预算选择。

政策来源筛选必须覆盖退款政策及售后手册，不能因为后者 content_type=manual 被排除；商品手册不能代替政策闸。任何检索异常、过期索引或无充分政策证据均停止资格判断并明确兜底。

多查询改变候选分布，新建第 6 章检索校准产物，并绑定真实文档、查询方式、扩写 Prompt 和重排配置指纹；不直接复用第 5 章 raw-query 阈值。

## 8. interrupt、恢复与聊天状态

复用官方 AsyncSqliteSaver 与现有会话 thread_id，不使用只存在前端的暂停标记。缺客户ID/待选单可进入等待状态；卡片路径必须真实调用 interrupt，使用匹配的 Command(resume=...) 恢复。

interrupt 载荷至少包含 kind、turn_id、可显示提示与可选订单商品项；客户端另携带实际 interrupt_id。订单卡片只显示当前声明客户的记录，包含商品名/规格、订单号、数量、实付、状态及时间；不展示其他客户列表。后端拒绝客户端提供的金额、状态、政策结论，以服务端订单数据为准。

恢复校验 conversation_id、turn_id、interrupt_id、当前等待状态、customer_id 与 order_id/item_id 匹配关系。ID错误或订单已变化时显示明确错误或刷新选择，不推进旧状态。

暂停节点恢复会从头执行；付费改写、Jev、扩写、检索位于独立已完成节点，不能在等待节点前半段重复执行。节点中的读取须无副作用；提交退款单不放在 interrupt 前。GraphInterrupt 作为正常控制流穿透，不被宽泛异常捕获转成失败日志。

暂停状态为 waiting_customer 或 waiting_order，与 complete/failed/cancelled 区分。SSE发送 interaction_required 后以 paused 结束本次连接，不发送表示业务完成的 done。释放当前HTTP请求锁，但保留持久化待处理状态；后续请求仍受同会话单写限制。

刷新页面/重启服务后，历史接口读取 SQLite 权威等待状态并恢复卡片；MySQL保存用户消息及等待展示信息。两套存储写入并非跨库原子事务，按稳定 turn/interaction 标识对账；持久化失败不发成功暂停/完成事件，不重放提交副作用。

重复点选返回已消费或处理中状态，不再次分类、生成答复或建单。取消等待或改变客户ID会使旧卡片失效；切换普通诉求时显式终止旧等待，再启动新一轮，避免旧退款流程在后台继续。

## 9. 退款单与动作边界

退款表单是创建“退款申请”，不是支付退款执行器。没有支付接口时不能声称资金已退回；该限制写入 UI 回执与演示说明。

主力 Agent 在有订单和政策证据后，可返回可申请、不可申请或信息不足的结论及引用。只有可申请才给出表单入口；信息不足时澄清影响资格的事实，不追问退款原因枚举。售后请求按用户目标判断维修/换货等，不能一律强行转退款。

表单显示已选订单商品项及商品项实付金额，原因下拉来自 refund-reasons.md；用户选择原因并点击提交才建单。最简版申请该商品项全部数量/实付金额，不新增任意金额编辑或支付执行。政策支持部分退款但缺少协商金额时交人工，不自动计算赔偿。

提交前重新校验订单归属、当前状态、商品项、原因编码、证据/资格上下文有效性；若选择的原因改变原资格判断依据，应先按已加载证据复核，证据不足则重新检索或澄清，不直接沿用旧结论。已退款或存在活跃重复申请时返回明确状态。

申请记录使用现有 MySQL 新增独立表，保存申请号、会话、客户/订单/商品项、数量、金额、原因、来源版本及时间；事务与幂等键保证同一提交仅创建一次，重复请求返回同一申请号。源 orders.md 与 logistics.md 只读，不把生成结果写回原始订单。通过申请表叠加展示本系统待处理状态。

## 10. 接口与模块边界

模块职责：query_resolver、jev_classifier、intent_policy、business_data、aftersales_workflow、refund_service；复用 workflow_graph/service/repository、现有检索器及配置入口。不新增前端框架。

接口建议（为本项目待实现契约，不是声称已存在的框架 API）：

- 现有 POST /v1/chat/stream：保留完成聊天事件，新增查询准备和 waiting 事件。
- POST /v1/conversations/{id}/interactions/{interrupt_id}/resume：校验后按同线程恢复并流式返回；请求携带 turn_id、request_id 与回填值。
- POST /v1/conversations/{id}/interactions/{interrupt_id}/cancel：使待处理交互与旧卡片失效。
- GET /v1/conversations/{id}/messages：增加可恢复的 pending_interaction；公开分类对象仍仅 intent/confidence。
- POST /v1/conversations/{id}/refunds：用户确认后创建申请，含 server-issued action_id、reason_code、request_id；订单、金额取服务端绑定。
- 原因选项随服务端表单载荷返回；客户端不硬编码另一份枚举。

新增状态不复用现有 knowledge confidence 字典：意图判断、检索置信与业务资格分别存储，避免字段覆盖。日志保留阶段、故障码、版本、阈值、时间与调用量；普通业务日志不记密钥、完整 Jev 请求或整份订单文件。查询/分类可见调试只包含用户当前必要上下文与结果，不暴露推理文本。

## 11. 评估、阈值与验收

### 真实标注评估

- 单轮意图至少每类20条，按类别分为10条校准、10条独立验收；另加24条边界/未知样例及12组物流→退款→物流多轮对话，按整段对话划分两套集合，防止相邻轮泄漏。
- 为每轮标注原话、相关历史、可接受完整问题/约束、应否逐字透传、意图、允许的候选对象、应走路线。扩写标注不得丢失或新增的条件及应覆盖条款。
- 先冻结验收集，用真实 Jev 保存八类概率、confidence、预测、耗时和实际模型版本。按原始分类准确率、混淆矩阵、误路由、弃权率分别报告，不能用全部落其他伪装高准确率。
- 在校准结果中枚举实际 confidence 候选切点；优先满足退款/售后自动路由无错误样例，并在此前提下最大化业务覆盖。允许为核心场景设置独立阈值，但都保存在一个集中产物中；无满足条件且具有正确自动路由样例的阈值则该类不开自动路由并报告。
- 冻结 criteria/阈值后跑独立验收；核心多轮和用户四条验收链路必须逐轮正确，高风险误路由为零。阈值导致核心验收弃权也算未通过，不能降低标准掩盖问题。
- 报告原始分类准确率与各类召回率，不以 confidence 数字宣称泛化正确率。校准样本量有限，零误判只指本次样例。
- Prompt/criteria 修改后按版本保存结果；不反复用验收集调参，不无限重试直到某次通过。真实请求数量和费用在运行前由计划列出，失败也计入记录。

### 浏览器验收

1. 完整问题逐字透传；多轮对象已明确的“这个能退吗”先显示补全后的问题，再显示退款退货路由。
2. 不带订单号发起退款，询问客户ID；提供后显示仅该客户的订单商品卡片。
3. 点选后继续原来的子流程，顺序可见为订单读取、扩写、政策查询、最终答复；刷新后卡片可恢复，重复点击无重复建单。
4. 从物流到退款再回物流，每轮意图正确，不继承过期申请动作。
5. 无法可靠归类的怪问题进入其他；Jev失败/低置信不会进入退款路径。
6. 可申请时显示表单，原因固定下拉，提交后返回申请号和待处理状态；不可申请/信息不足不伪造成功。
