# 第 5 章：确定性 Workflow 与主力 Agent 设计

状态：设计草案已整理，等待用户审阅；不是实施授权或功能完成报告。

## 1. 目标与已确认边界

将现有“最多一次工具调用”的聊天流程升级为 LangGraph 确定性编排，主力 Agent 在允许的分支内运行 ReAct 循环。先保留可独立演示的无编排框架裸循环，再以相同工具、输入输出和预算约束重构为图。

用户已确认：

- 意图识别可以调用一次模型；判为闲聊后返回固定话术，不再调用回答生成模型。
- 使用 SQLite checkpointer。保持现有单实例、单 worker 部署，不新增 PostgreSQL，不将本章成果宣称为多实例高可用系统。
- 转人工后的问候精确为 `您好,我是SayHelp,请问有什么可以帮您的`。
- 查订单、查物流、建工单等复用第 2 章业务工具；知识检索复用第 3/4 章检索器。
- 指代消解本章原样透传；不实现正式意图识别、上下文策略升级、MCP 业务接入或飞轮入库。

## 2. 架构选择

采用外层 StateGraph 固定业务路径、内层 Agent/工具节点循环的结构。外层决定是否允许进入 Agent，内层决定查询哪个工具及是否继续；节点间统一通过 State 传递数据。

对比方案：把裸循环整体装进一个图节点虽然改动较少，但检查点只能看到整体节点边界，中间工具步骤不清楚；将所有步骤平铺进一个大图虽然直接，但容易混淆固定业务路径与 Agent 决策。推荐外层 Workflow + Agent 子图，复用同一组模型与工具适配器，裸循环仅用于教学演示和行为对照，不形成另一条线上业务入口。

裸循环的“无框架”指不使用 LangGraph 或现成 Agent 执行器来控制循环；直接编写模型请求、解析工具调用、执行现有工具、回灌结果、停止的流程。允许复用现有模型客户端和第 2 章工具对象，不重写业务工具。

## 3. 固定图骨架与七类分流

入口 → 指代消解（原样透传）→ 意图识别（JSON）→ 代码分流 → 分支执行 → 日志记录 → 结束。

| 意图 | 出口 | 路径 |
| --- | --- | --- |
| 商品咨询 | 知识类 | 强制检索 → 置信度闸 → 通过后进入主力 Agent |
| 退款退货 | 知识类 | 强制检索政策 → 置信度闸 → 通过后进入主力 Agent，可再查订单 |
| 物流 | 业务数据类 | 直接进入主力 Agent，自行查工具 |
| 订单 | 业务数据类 | 直接进入主力 Agent，自行查工具 |
| 售后 | 业务数据类 | 直接进入主力 Agent，缺信息则追问 |
| 投诉 | 投诉 | 固定安抚回复 + 两个独立可选项，不进入 Agent |
| 闲聊 | 闲聊 | 固定回复，不进入 Agent、不检索 |

分类输出只有一个受枚举约束的 intent 字段；拒绝未知标签、无效 JSON 和额外字段。分类失败返回受控提示并记录原因，不默认放行到 Agent。分类 prompt 的规则明确退款退货优先于泛售后，明确投诉诉求优先，物流查询优先于仅因提到订单号就归为订单。用标注样例验证歧义输入，保留逐题预测与调用次数。

投诉话术：`很抱歉给您带来不好的体验。您可以选择转人工或建立工单，也可以继续向我说明情况。`

闲聊话术：`您好，我是 SayHelp。可以帮您查询商品、订单、物流、退换货政策或售后问题。`

## 4. 检索与置信度闸

知识分支直接复用第 4 章 RagRetrieval 的 hybrid_rerank 路径，复用现有证据与引用结构。原始问题透传构造检索输入，不继续调用第 4 章正式查询理解/答案自评链，避免替代本章指定的简化节点或在 Agent 后再做闸。

置信度最简实现复用现有 ConfidencePolicy：无证据或最高重排分数未过配置阈值即拒绝。记录分数、阈值、证据 ID 与原因；现有校准依赖查询处理方式，因此必须用本章的标注知识样例验证复用阈值的行为，必要调整仅写本章独立配置/评估产物，不覆盖用户正在修改的 ch04 文件。

通过后把问题、通过闸的证据和引用编号交给 Agent；弱证据直接返回 `目前没有足够的可靠资料回答这个问题，请补充具体信息或联系人工客服核实。`，不产生 Agent 调用。检索不可用与弱证据区分记录，均不放行编答。

弱证据问题先写本章本地结构化日志（原问题、会话/轮次标识、原因、时间），运行日志目录加入 Git 忽略；不写飞轮入库管线，不启动挖掘任务。业务类不经过此检索闸。

## 5. 主力 Agent、停止与预算

循环为：调用模型 → 有工具调用则校验执行并添加对应工具结果 → 再调用模型；无工具调用时输出最终回复或追问并结束。每个调用 ID 必须唯一且有配对结果，失败结果也回灌；不得丢弃部分工具调用造成无效消息序列。

自动执行工具采用显式只读允许列表，复用现有 query_order、query_logistics 及合适的知识查询适配器。create_ticket 不进入 Agent 可执行列表；知识工具若被调用，仍使用复用的检索与闸，不能绕过证据约束。演示订单和物流数据继续明确标注模拟，不伪装真实数据。

Agent 可以输出零个、一个或两个建议动作。建议使用结构化结果信号，可通过无业务副作用的控制信号表达；它不是新增业务工具，也不执行转人工或建工单。正文不使用关键词匹配来决定按钮。

默认每轮最多 6 次 Agent 模型调用、6 次实际工具执行；同一工具和参数连续失败两次停止重复尝试。每次调用沿用已有上下文预算和输出上限，另设本轮累计 token 预算（默认 12000，包含分类）；请求前按输入估算与输出预留检查，调用后记录模型 usage，缺失 usage 时明确标注估算。超限、超时、非法工具调用返回受控说明，不以无限重试消耗 token。

不升级历史压缩策略，仅扩展现有消息配对恢复逻辑使其兼容多步工具调用，避免下一轮丢掉复杂问题的已完成上下文。

## 6. 流式接口与状态

保留现有聊天 SSE 入口和历史页面。知识证据闸必须先完成，才允许任何 Agent 正文 token 输出；只向前端发送用户可见回复，分类 JSON、工具参数和内部决策不作为正文流出。工具状态、引用和可选动作使用独立事件。

Agent 最终答复使用真实模型流。工具决策阶段的内容不能被误当作最终答复；适配器负责识别模型返回的工具调用与终止回复。若上游模型流协议不能可靠区分，先查官方接口并验证后调整方案，不悄悄将整段生成后切片伪装为实时生成。

State 保存会话 ID、轮次 ID、消息、原问题/透传问题、意图、分支、检索证据、置信结果、步骤数、token 用量、建议动作、完成/失败状态与最终消息 ID。只保存可序列化数据，不把数据库连接、工具对象、模型客户端放入 State。

使用官方 AsyncSqliteSaver，以现有 conversation_id 的字符串作为 thread_id。由应用生命周期打开/关闭文件连接；检查点文件、WAL/SHM 文件均不入 Git。重启后同一会话恢复已完成状态，其他会话隔离。每个新用户轮次重置检索结果、动作建议、预算等轮次字段，避免旧建议触发动作。

MySQL 保留业务表和 UI 历史；SQLite 保存图运行状态，不把 MySQL 历史写入伪称为 checkpointer。新图首次接管旧会话时仅导入完整历史。保留单会话互斥；删除会话后拒绝恢复其图状态。中断轮次标记为未完成，新用户消息正常开启新轮次，不自动重放任何业务写入。

SQLite 与 MySQL 不是同一个事务。历史写入使用稳定轮次/消息身份防止图恢复时重复追加；测试模拟一侧成功另一侧失败，失败不得发送完成事件。必要的持久化标识迁移纳入实施计划，不宣称跨库原子事务。

## 7. 两个独立按钮

投诉固定携带 handoff 与 create_ticket 两个建议；Agent 可返回任意子集。前端使用两颗独立按钮，不给默认选中项；用户忽略它们继续聊天时，不产生后端动作，也不进入等待批准的图中断状态。

- 点击“转人工”：前端本地追加 `已转接人工客服`，随后追加 `您好,我是SayHelp,请问有什么可以帮您的`。不调用工单接口、不写 tickets、不改变后端会话为真人接待状态；本章仅模拟视觉效果。按钮点击后禁用，避免重复问候，另一颗按钮仍可独立使用。
- 点击“建工单”：前端展示独立确认交互，显示可核对的问题描述和工单类型；取消不发送写请求。确认后调用专用接口，由服务端绑定当前会话并复用第 2 章 create_ticket 工具写 tickets。成功只提示工单号及待处理，不提示已经转人工。

必须同时修正原 create_ticket 的返回话术与 Repository.create_ticket 的 `conversation.status = '已转人工'` 副作用，保留原业务工具并调整语义，不新建第二套工单业务实现。

接口校验会话存在且未删除、动作标识属于该会话、描述/类型合法。使用稳定提交标识与数据库去重约束处理重复点击/网络重试，重复确认返回同一工单；写工具不盲目重试。若超时后结果未知，前端明确显示未确认，不生成假成功信息。

建议动作须可随历史回复恢复；状态持久化格式与现有消息 schema 的兼容迁移在计划中明确。前端所有用户/模型文本通过安全文本渲染，保留引用、置顶、删除和历史加载行为。

## 8. 日志、异常和验收

每轮结构化记录经过的节点、意图/分支、工具名与调用 ID、耗时、检索闸决定、停止原因和 token 消耗。日志记录覆盖成功、拒答及异常路径；不记录密钥、模型隐藏推理或完整工具返回敏感数据。

实现代码走 TDD，先观察失败再修复；纯分类 prompt 和检索门槛用标注集评估，不写只验证 prompt 字符串的伪测试。测试不污染真实客户会话与知识库。

验收包括：

1. 政策问题日志强制经过检索与闸；弱证据 Agent 调用次数为零。
2. `订单 1001 的物流到哪了` 由 Agent 自行调用物流工具。
3. `我要投诉` 不进入 Agent，两颗按钮独立；只点转人工 tickets 不变，取消建单不写入，确认建单仅新增一个工单且不改变为已转人工；均不点也能继续聊天。
4. 闲聊仅一次分类调用、固定回复。
5. `先查订单 1001 的订单状态，再查它的物流，分别告诉我结果` 能看到多步模型—工具—模型循环；不将一次并行调用两个工具误报为多步 ReAct。
6. 缺订单号会追问；预算、工具失败/超时、无效分类、用户断开均有受控终止。
7. SQLite 重启恢复与会话隔离、多步历史恢复、动作不串轮、重复工单确认、现有引用/历史 UI 回归。

最终交付包含裸循环演示、图流程演示、启动命令、测试与评估实测结果、开发记录路径。验证完成后按仓库要求提交并推送；不提交 .env、密钥、运行数据库或用户原有未提交文件。
