# 第 7 章：会话内三层上下文管理设计

状态：2026-10-15 用户以“设计通过”批准，brainstorm 定稿；不是实施计划批准或功能完成声明。

## 1. 目标、基线与方案

用户要求“只管当前会话，不跨会话、不存用户画像”，完整历史不丢失，压缩只服务模型窗口；默认配置连续 20 轮以上不降级，缩小窗口演示降级、异步摘要及最初订单的回忆。

以 codex/ch06-intent-router 的 7131515 为实现基线，后续建立独立 ch07 分支，保留第 6 章 Jev 分类、保守兜底、售后 interrupt 与回执恢复。不在旧 main 上重写图，不改用户现有知识文件，不重做已被用户拒绝追加额度的 ch06 校准。

候选方案：

- 推荐：MySQL 保存对话原文、两个边界和追加摘要；既有 LangGraph SQLite checkpoint 保存完整图消息；独立上下文构建器为模型产生精简视图。复用现有存储与生命周期，改动集中在接缝。
- checkpoint 同时承担摘要权威存储：少一处读取，但违反独立会话摘要表要求，且后台任务写图状态易与活跃轮次冲突，不采用。
- 新增外部队列执行摘要：利于多机扩容，但本章增加基础设施负担。先用应用生命周期内异步工作器、MySQL 任务租约和幂等提交；保留任务接口供以后扩展。

技术不替换：LangGraph add_messages + checkpoint、LangChain trim_messages、SQLAlchemy/MySQL。SQLite 仅沿用现有 checkpoint，不替换会话业务库。

## 2. 数据与边界

conversations 增加 summary_upto_msg_id（摘要已覆盖的最后一条业务消息）、layer1_from_msg_id（层 1 首条用户消息）、上下文版本及摘要任务租约字段。NULL 分别表示尚无摘要、尚无完整历史。边界按本会话消息排序，不能假设自增 ID 连续。

新增 conversation_summaries：conversation_id、段号、起止业务消息 ID、摘要正文、估算 tokens、来源批次指纹、创建时间；段号和批次范围有唯一约束。摘要正文只追加，禁止改写/合并旧段。摘要追加和 summary_upto_msg_id 前移在同一 MySQL 事务内提交。

- 层 3：已摘要覆盖的完整轮次；注入其摘要，不再注入该段逐条消息。
- 层 2：summary_upto_msg_id 之后、layer1_from_msg_id 之前的完整轮次；用户原文保留，客服正文保留前 60 个 Unicode 字符，工具结果替换为含工具名/调用 ID 的单行标识，保留调用与结果配对。
- 层 1：layer1_from_msg_id 起的完整轮次；原文和工具调用/结果不裁字、不压缩。

调整层级仅修改边界，不能移动/删除原文。降级以完整轮次为单位，不能拆散工具调用和结果。本轮及尚未完成/等待恢复的轮次不参与摘要。摘要完成只覆盖任务启动时冻结的上界，不能追到任务期间继续前移的层 1 起点。

messages 继续保存用户原文和最终答复及现有展示元数据；停止新增大块工具结果，历史已有工具行不删除。checkpoint 保存完整业务消息和工具轨迹，并通过 turn_id 和稳定消息 ID 对应业务消息范围；不能用消息表条数推测工具占用。

## 3. 完整 State 与模型视图分离

移除每轮 REMOVE_ALL_MESSAGES + 已裁剪历史的重置流程。每轮仅提交新增 HumanMessage，各节点仅输出新增 AIMessage/ToolMessage，由 add_messages 按稳定 ID 合入。摘要、证据与模型用 system 不作为逐轮业务历史追加。

旧会话首次迁移：checkpoint 存在时对账增量；缺失时由 MySQL 可用原文重建，缺少旧工具轨迹要记录，不伪造完整工具结果。持久化失败、重复恢复及完成 checkpoint 后回执失败沿用幂等对账。后台摘要不修改 graph State，下一轮读取已提交边界。

ContextView 是独立的瞬时值，包含摘要段、层 2/层 1 消息、覆盖范围、估算明细；不回写 messages reducer。trim_messages 使用统一 token_counter、strategy='last'、allow_partial=False，并额外按完整轮次校验边界。对未降级的层 1 比较原文和工具数据一致性。

## 4. 输入顺序与共享历史

主力 Agent 请求顺序固定为：固定 system 人设与红线 → 层 2 → 层 1 → 当前用户原句 → 一条非 system 背景消息（全部早期摘要 + 本轮检索证据）→ 本轮 ReAct 追加调用/结果。背景使用 HumanMessage，明确标记为不可信参考资料；无背景时省略。只发一个固定 system，不把摘要、证据或当前客户字段拼入 system。

工具定义用固定排序及固定 schema，通过模型 tools 参数绑定，禁止把动态客户值写进 schema。缓存收益依赖上游模板；验证请求载荷稳定前缀，不声称仅靠本地顺序就保证命中缓存。工具选择与最终生成使用各自稳定的请求模式，记录 tools_bound。

QueryResolver 使用同一摘要与滑窗视图，移除其独立 8 条/6000 字限制；订单号等事实守卫允许从有来源的摘要提取已出现编号。Jev 继续只分类消解后的完整 Query，不改既定 API 契约。history_ctx 表示共享历史，而不是谎称 Jev 直接接收全历史。

## 5. 可核对预算

用户已授权：“由你。根据实际提示词、工具定义和 ReAct 峰值制定可核对的公式”。因此 5650/3954/1695 不再作为必须凑出的常量。

### 统一估算

初始统一使用 count_tokens_approximately(chars_per_token=1.0, extra_tokens_per_message=3.0)，包含角色、工具调用 ID、参数和 tools schema。这是保守近似，不宣称对所有模型严格等于或大于真实 tokens。业务预算、trim_messages、工具结果准入、摘要触发和日志必须使用同一函数；禁止消息除 4、工具除 3、证据除 1 混用。

后续校准在固定中英混合样例上比较 provider usage 与本地估算，记录模型 ID、库版本、prompt/schema 指纹、偏差和安全余量。调整 chars_per_token 时必须重跑全部预算回归与两种演示，不能只改计数函数。不可用 provider usage 时明确标记估算未校准。

### 公式和约束

定义 W 为配置的模型窗口；F 为实际固定 system + 实际 tools 的估算；R 为本轮完整检索证据及其引用包装占用；S 为全部已注入摘要及包装占用；O 为最大输出预留；U 为当前用户消息占用；G=ceil(W×5%) 为初始安全余量。

设 K=MAX_AGENT_STEPS（明确表示最多 K 次工具选择/反馈，之后最多一次最终生成，不包括独立的指代消解/Jev），A=512 为现有 selection 输出上限，X=TOOL_RESULT_MAX_TOKENS，B 为每一步额外协议开销。P=K×(A+X+B) 为历史之外的当前轮 ReAct 峰值。

B 初始最低预留 32，并根据实际 tool_call_id/name/序列化包装取更大的值；运行时核对完整 batch。X 限制的是每一步所有工具结果合计，不是每个结果都可占 X；保留配对错误结果需要的空间。超大结果使用明确的预算拒绝结果，不把截断 JSON 当作正常结果。当前轮结果进入 State 后保持原样。

H_available=max(0,W−F−R−S−O−U−G−P)。H=min(N×T_steady,H_available)，L1=floor(7H/10)，L2=H−L1，保证取整不漏 1 token。T_steady 是标注演示轮次实际测得的稳态占用，初始规划值 1024，N=32；两者均配置并输出，不作为窗口常量。

启动按 U_max、R_max 和摘要初始预留 S0 推导最坏账本；每轮按实际 U/R 和 max(S0,S) 计算。证据上限 R_max=RERANK_TOP_K×512（含引用元数据），按完整证据条目准入，过长条目不截成半段政策。固定提示、证据包装、摘要包装或工具定义变更均自动重计 F/R/S。默认 RERANK_TOP_K=5、S0=512、MAX_OUTPUT_TOKENS=2000、MAX_USER_INPUT_TOKENS=2000、MAX_AGENT_STEPS=3、TOOL_RESULT_MAX_TOKENS=1200。

默认应用窗口拟为 65536；启动必须确认部署模型支持该窗口，超过已知模型能力拒绝配置，未知能力须明确配置且日志标记未核实。演示仅将窗口设为用户给定 18000，其余按用户六项配置执行。默认 20 轮不压缩以冻结演示样例验证，不承诺任意 20 轮满额工具输出均可无损装下有限窗口。

启动自检将固定前缀、最大当前输入、峰值和输出预留合计，与 W 比较；放不下一轮就报“上下文预算不足”并列出分项。历史分配为零也报警。每次调用前重新计算真实完整载荷 + 本次输出上限，超限绝不发送。跨多个模型调用的累计费用预算与单请求窗口是两回事：保留独立调用/累计 tokens 闸，按请求计划重新推导默认累计预算，不能让旧 12000 累计限额把新窗口提前卡死。

## 6. 降级与异步摘要

历史全能放入层 1 时不移动边界。层 1 超预算才按完整轮次推进 layer1_from_msg_id，层 2按规则表示后重新计数；层 2 超 L2 才触发摘要。超预算依据实际视图 tokens，并另记原始工具占用，绝不以行数代替。

每会话只运行一个摘要任务；MySQL 短事务领取租约并冻结范围，事务外调用模型，完成后用版本/租约/边界校验提交。任务可在用户回复流进行时运行，不 await 摘要结果；只有短事务，不持有跨网络锁。应用关闭有有界清理，租约过期可恢复；重复触发、空范围、过时结果均记录 skip，不重复追加段。

提示词要求仅提炼商品、明确订单号/手机号、诉求和未解决问题；区分用户陈述与客服/工具确认，不把提问或承诺当作已完成事实。每段目标 50–200 个中文字符；旧摘要只作背景，新摘要只覆盖本批，不复制或合并旧摘要。检查编号必须来源于本批，空闲聊可产生无事实的空段及覆盖记录。结构验证失败/超长/超时保留原边界，后续有界重试，不能用伪摘要前移。

后台未完成时仍以旧摘要 + 未摘要层 2 + 层 1 构造输入。允许层 2暂借实际请求剩余空间，完整载荷硬闸仍生效；若仍装不下则本轮快速给出预算不足提示，保留原文，不等待后台也不静默跳过事实。成功摘要从下一次构造视图生效。

所有摘要段均保留并按时间顺序注入，S 随段数增长重算。有限窗口不能无限容纳追加摘要：最终摘要本身过大时明确提示新开会话，不重新压缩旧摘要，也不暗中丢掉最早段。20+轮验收应远未达到此边界。

## 7. 可观测与多会话

每个主力模型实际调用前写 log/app.log 的 model_ctx：conversation_id/turn_id、phase、摘要全文、逐条发送消息和角色/工具字段、工具定义及其指纹、窗口条数、tokens 分项、两个锚点。日志取自传给适配器的同一请求对象；不能只记录一个构建后又被修改的候选。保留应用数据，不记录 API headers/密钥或隐藏推理。

每轮入口和恢复轮都写 history_ctx（摘要全文与共享窗口）；指代消解调用前记录实际历史视图，无 Agent 的闲聊/兜底也有记录。summary trigger/start/done/skip/failed 都含任务 ID、冻结范围、段号、耗时和原因；成功日志使用“summary done 第N段”，降级日志使用“层1 降级 X→Y”。

复用现有前端侧栏，添加已摘要标记，按新近会话排序；新对话不删除旧会话，切换回载完整用户/客服原文及现有卡片。GET /api/conversations 与 GET /api/conversations/{id}/messages 为只读；保留旧 /v1 路由的兼容行为。

同一浏览器用服务端随机生成的稳定访客 cookie 关联该用户会话，列表及详情都检查归属；不以售后客户 ID 充当访客身份，不建立用户画像。旧会话不自动全部认领到当前访客；无旧归属凭证的历史采用明确迁移/开发数据方案，不公开全库历史。列表分页可加载全部，首问预览与摘要标记由数据库查询生成。侧栏失败静默，聊天主流程继续；切换请求防止晚返回覆盖新会话。

## 8. 验证、交付和流程

按 Superpowers 在书面设计获批后写实施计划并评审，用户选择执行方式后实现。实现代码按 RED/GREEN；摘要 Prompt 使用冻结标注样例评估，不以字符串断言冒充语义验收。每阶段即时追加 dev-notes/ch07.md 的原话、产出、纠偏和返工。

测试覆盖预算算术/取整/中文估算、只移动锚点、工具配对、历史不变、异步非阻塞、失败与租约恢复、并发去重、暂停恢复、摘要来源与抗编造、API 归属与前端切换。真实 MySQL 验证摘要事务和幂等；checkpoint 重开后核对完整历史；浏览器验证多会话及侧栏失败。

冻结至少 24 轮包含早期订单/手机号/商品/未解诉求及大工具结果的样例，在默认与演示窗口各跑一次，验收默认无降级/摘要、演示出现完整级联、最初订单追问正确。另设摘要失败/慢任务故障注入证明当前回复不等待摘要。后台任务忙时极端超限的受控提示单独测试，不伪称所有压力均能正常回复。

实施计划需列真实模型调用上限、按轮统计与结果文件；不沿用 ch06 已拒绝的额外校准额度。最终给出可直接运行的预算检查/两配置演示命令、测试结果、日志定位与 dev-notes 路径；当前文档不宣称功能已可演示。独立 code review 后修复问题，再提交推送 GitHub。
